# Application data infrastructure

Each `staging` and `production` Pulumi stack owns a separate resource group,
PostgreSQL 16 Flexible Server/database, Storage Account/private Blob container,
and managed identity. AKS/network/ACR remain in `aks`; cluster add-ons remain in
`app-tools`. App releases in `deploy/` do not own or delete this data.

## Passwordless access

AKS Workload Identity federates `system:serviceaccount:ENV:demoapp-data` to that
environment's managed identity. The app requests short-lived Entra tokens for
PostgreSQL and Blob Storage; there are no DB passwords or storage account keys in
runtime configuration. PostgreSQL password authentication and Storage shared-key
access are disabled. Blob Data Contributor is scoped to the individual container.

PostgreSQL uses a separate SQL principal mapping: `bootstrap.py` connects as the
configured Entra administrator and maps the identity's **object/principal ID** to
the non-admin `demoapp` database role. Azure IAM alone does not grant SQL access.
The role can connect and create tables in the app's schema for startup initialization.
The app obtains a token for each new connection; the SDK caches/refreshes tokens.
TLS verifies the server certificate and hostname.

The bootstrap helper owns the namespace's `demoapp-data` ServiceAccount and
`demoapp-runtime` ConfigMap. The Helm chart references them and marks pods for the
AKS identity webhook. It does not own those resources. Endpoints and IDs are not
secrets. Local Docker Compose still uses its local PostgreSQL password and Azurite
connection string; workload identity is only used for Azure deployment.

## First deployment

Prerequisites: Python 3.12+, Pulumi CLI 3.266.0, Azure CLI, kubectl/kubelogin,
access to the existing AKS Pulumi backend, and an Entra administrator identity.
The deploying Azure identity needs data-resource/identity management rights,
resource-group creation, and permission to assign the container-scoped data role
(e.g. Contributor plus Role Based Access Control Administrator at suitable scopes).
It also needs Storage Blob Data Contributor on the existing state backend.
Register `Microsoft.DBforPostgreSQL` if the subscription has not used it before.

```sh
cd infra
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
az login
pulumi login 'azblob://YOUR_STATE_CONTAINER?storage_account=YOUR_STATE_ACCOUNT'
pulumi stack init staging --secrets-provider passphrase
# Preserve any encryption metadata generated by stack init when adding config.
```

Use `Pulumi.example.yaml` as the configuration reference. Configure `aksStack`,
`entraAdminObjectId`, `entraAdminName`, `entraAdminType`, and `postgresAllowedIps`
in the stack file. `entraAdminType` is `User`, `Group`, or `ServicePrincipal`.
Use the Entra UPN for a user (including the full guest UPN for guest accounts).
The bootstrap operator must be able to obtain an Entra token for that admin role.
Keep the stack's encryption passphrase available for state operations even though
runtime outputs contain no passwords. Stack files and `.secrets/` are ignored.

```sh
.venv/bin/python -m unittest discover -s tests -v
pulumi preview --stack staging --diff
pulumi up --stack staging
```

Repeat with `production`, using independent resources and identities. Both stacks
read subscription, tenant, region and OIDC issuer from the AKS stack. Keep state
in the **same existing backend** as AKS for stack references, not in the new photos
account. Only the exact environment names `staging` and `production` are accepted.

## Allowed IPs

The PostgreSQL firewall needs the **application's outbound public IP(s)** to allow
AKS connections. Your PC's public IP is additionally needed for SQL administration
and bootstrap. Inbound ingress IPs and internal pod/node addresses are not the
right values for this public PostgreSQL endpoint. Authentication is still required.

For the existing load-balancer-based AKS egress:

```sh
az aks show --resource-group YOUR_AKS_RG --name YOUR_AKS_NAME \
  --query 'networkProfile.loadBalancerProfile.effectiveOutboundIPs[].id' -o tsv
az network public-ip show --ids YOUR_PUBLIC_IP_RESOURCE_ID --query ipAddress -o tsv
```

Resolve every ID. Update the firewall if AKS egress or your PC's public IP changes.
The configuration rejects CIDRs, private/documentation addresses and `0.0.0.0`;
it does not enable access from all Azure services. Blob Storage has an authenticated
public HTTPS endpoint; a private container does **not** imply a private endpoint.

## Bootstrap and verify

After Azure provisioning finishes, connect kubectl to the cluster identified by
`clusterName` / `clusterResourceGroup` outputs:

```sh
az aks get-credentials --resource-group YOUR_AKS_RG --name YOUR_AKS_NAME
kubelogin convert-kubeconfig -l azurecli
.venv/bin/python bootstrap.py --stack staging --context YOUR_AKS_CONTEXT
.venv/bin/python bootstrap.py --stack production --context YOUR_AKS_CONTEXT
```

Run from an IP allowed by the database firewall. Azure CLI must be signed in as
the configured Entra admin (or an eligible member of the configured admin group).
The helper is repeatable and refuses a conflicting existing app principal mapping.
Tokens remain in process memory. No runtime Secret is created. Restart existing
app pods after changing runtime endpoints; projected identity tokens refresh
without restarting pods. Existing password-owned tables need a separate ownership
migration before adopting this bootstrap flow.

Deploy the updated app image and chart via [the release guide](../deploy/README.md).
The cloud chart enables workload identity; the old image does not support this
configuration. Verify health, upload, image download, and guessing in staging
before promoting the application. A storage deployment alone does not release
the updated application code.

## Manual GitHub deployment

`.github/workflows/data-infrastructure.yml` runs from `main` with environment and
`apply` inputs (preview by default). It previews and optionally provisions Azure
resources. It does not perform SQL bootstrap or deploy Kubernetes workloads.

Create `data-staging` and `data-production` GitHub environments restricted to main.
Configure production reviewers if desired. Each needs:

| Setting | Kind | Value |
| --- | --- | --- |
| `AZURE_CLIENT_ID` | Variable | Data-provisioning identity |
| `AZURE_TENANT_ID` | Variable | Platform tenant |
| `AZURE_SUBSCRIPTION_ID` | Variable | Platform subscription |
| `PULUMI_BACKEND_URL` | Variable | Existing `azblob://...` backend |
| `PULUMI_STORAGE_ACCOUNT` | Variable | Existing state account |
| `PULUMI_STACK_CONFIG` | Secret | Entire matching `Pulumi.ENV.yaml` |
| `PULUMI_CONFIG_PASSPHRASE` | Secret | Matching state encryption passphrase |

Federate the workflow identity with issuer `https://token.actions.githubusercontent.com`,
audience `api://AzureADTokenExchange`, and subject
`repo:OWNER/REPO:environment:data-staging` or `...:data-production`. This provisioning
identity is separate from both the ACR publisher and runtime workload identities.
Keep the GitHub stack configuration synchronized with local changes. The existing
backend must be reachable by the runner. Initial stack creation remains a one-time
local step; the workflow can then perform the first resource update.

## Defaults, protection and recovery

- PostgreSQL: `Standard_B1ms`, 32 GiB Premium SSD with auto-grow, seven-day
  point-in-time backups. SKU/tier/storage/retention are configurable. HA and
  geo-redundant backups are disabled in these economical defaults.
- Blob: Standard LRS, HTTPS/TLS 1.2+, versioning, 14-day blob/container soft delete.
  Versions consume space; no automatic version cleanup is installed.
- Protected data resources/resource groups survive normal app releases. Intentional
  deletion requires `protect: false` and a reviewed Pulumi update before destruction.
  Protection/soft delete do not replace recovery testing, and blob soft delete
  does not recover a deleted storage account.
- Restore PostgreSQL to a new server, adopt the resource into IaC and update runtime
  endpoints before switching traffic. These defaults do not offer regional DR.

Unit tests verify IaC permissions, identity wiring and token handling. CI also
checks SQL schema grants in disposable PostgreSQL; Microsoft Entra's extension
and actual identity federation require an Azure smoke test.

References: [AKS Workload Identity](https://learn.microsoft.com/en-us/azure/aks/workload-identity-overview),
[PostgreSQL Entra roles](https://learn.microsoft.com/en-us/azure/postgresql/security/security-manage-entra-users),
[Pulumi Azure Blob backend](https://www.pulumi.com/docs/iac/operations/stack-management/using-a-diy-backend/#azure-blob-storage).

The database name and application role are both `demoapp`. The PostgreSQL firewall

and the workload ServiceAccount/ConfigMap are installed in each namespace.
The data deployment does not publish or release the updated application image.

The local stack files are `Pulumi.staging.yaml` and `Pulumi.production.yaml`.
Their generated state encryption passphrase is stored locally, mode 0600, in
`.secrets/pulumi-passphrase`. Back it up in your password manager/secret store;
Git and Docker intentionally exclude it. From this directory, subsequent local
Pulumi operations can use:

```sh
export PULUMI_CONFIG_PASSPHRASE_FILE="$PWD/.secrets/pulumi-passphrase"
pulumi preview --stack staging
```

The administrator assignment is ordered after database and firewall creation:
Azure rejected concurrent Entra administration during initial server configuration.
Rerunning the update after those operations completed repaired the assignment;
refreshed previews then reported no changes in either stack.

Live verification passed in temporary AKS pods for both environments: application
initialization/health, non-admin SQL writes, Blob upload/download/delete, and denial
of access to the other environment's PostgreSQL server and Blob container. The
checks exercised the updated `api/main.py` with projected workload-identity tokens.
Temporary test pods/config maps were removed; normal application tables remain.
